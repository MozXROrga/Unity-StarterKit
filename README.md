# MozXR Unity Starter Project

Unity Sample/Starter Project for the MozXR Cluster setup.

## Overview

This is a Unity Sample/Starter project for the MozXR cluster setup.

It includes sample scenes to show how the MozXR Framework works and a starter scene with the required Mox components but otherwise empty.

## Requirements

- **Unity Engine**: 6000.3 or higher
- **Platform**: Windows 64-bit

## Setup

If you checkout the repository via git (rather than downloading a release package) you need to **download additional binaries**, available in the [release section](https://github.com/ArsElectronicaFuturelab/mozXR-Unity-StarterKit/tags).

Download and unpack the latest binary package. The package contains two folders, **Pharus** and **UnityEndpoint**.

The project already contains two default folders for these binaries, **Pharus** and **Endpoint**. Copy the the **content** of the two binary package folders to the respective empty folders of the project.

The result should look like

```
root/
├── Endpoint/
│   ├── Build/  
│   ├── Switchboard/
│   └──  project.json
├── Pharus/
│   ├── pharus-rec-sim-v2.4.0-s0-release_MultiCast_Floor/
│   ├── pharus-rec-sim-v2.4.0-s0-release_MultiCast_Wall/
│   ├── pharus-rec-sim-v2.4.0-s0-release_UniCast_Floor/

│   ├── TrackLinkSimulator_MulrtiCast_Floor/
│   ├── TrackLinkSimulator_MultiCast_Wall/
│   ├── TrackLinkSimulator_UniCast_Floor/
│   └── TrackLinkSimulator_UniCast_Wall/
├── StarterKit/
│   └── ...
└── ...
```

If you copy the binaries to the prepared folders as described you do not have to edit the MozXR configuration.

**Alternatively** you can keep the content of the binary package somewhere else, but you will need to set the propper paths in the **MozXR configuration** in the unity editor.

If you have multiple MozXR Projects on your computer you may chose to keep only one copy of the binary package at some other location than the default.

As described in [Configuration](#configuration), open the MozXR control panel (Tools -> MozXR -> Config) and change to **Endpoint Directory** and **Pharus Base Directory** to the correct locations.

## Basic Cluster Synchronization Concept

The Mox Cluster utilizes Unreal Engine's [NDisplay cluster](https://dev.epicgames.com/documentation/en-us/unreal-engine/ndisplay-overview-for-unreal-engine) capabilities. The Mox Unity Framework provides an interface to create projects in the Unity Engine and run them on a Mox Cluster setup.

The Unity Application will be running in the background and forward rendered frames via [Spout](https://spout.zeal.co/) to an Unreal Engine application which displays the frames and provides synchronization with other cluster nodes.

A Mox Cluster contains one primary node and any number of secondary nodes.

The synchronization concept assumes that changes to a running scene are only applied on the primary node. Common components of synchronized GameObjects are handled automatically. User-defined data may be added. See below for details on how to do that.

Synchronized GameObjects are split into a logic and a representation object. Visual and audio components of the original GameObject are moved to the representation object. User scripts, physics, etc. remain on the original (the logic object). The synchronization mechanism gathers updates (transforms and user data and such) from the logic objects on the primary cluster node. The updates are propagated over the cluster and then applied to the representation objects (on primary and secondary nodes).

Developers generally do not need to implement anything separately for primary/secondary nodes (more details below).

Non-synchronized GameObjects may be used, but visual/audio synchronicity cannot be guaranteed for those objects.

The camera setup is determined by an [NDisplay configuration](https://dev.epicgames.com/documentation/en-us/unreal-engine/ndisplay-overview-for-unreal-engine) specific to the cluster that the project is shown in. The Mox framework automatically sets up the unity camera at runtime accordingly.

## Getting Started

You can create your project largely like you would any other Unity project. Key differences are in how to utilize the automatic cluster synchronization and input forwarding provided by the Mox Framework.

To start with a new project you may copy and rename **EmptySample** in Assets/Scenes/. If not needed, you may also want to delete the Assets/Demo/ folder (unless you want to keep it around for reference).

### Demo Scene

A demo scene is provided as an example for all basic cluster synchronization mechanisms. It is found in Assets/Demo/Scenes/**SimpleDemoScene**. The other scenes in this directory are used to demonstrate synchronized level-switching.

Other than the required Mox Manager and Handler classes, the demo scene contains some objects to demonstrate movement, spawning/de-spawning, custom-data syncing, audio, and level-switching.

The following overview only includes demo-specific objects. That excludes standard Unity content and Mox Manager and Handlers needed in every scene.

```
SimpleDemoScene                 # Scene Root Object
└── Mox
    ├── MoxCameraHandler
	│   └── PharusVisualizer    # An object that holds a script that reads Pharus Tracking data from the MoxFramework and spawns simple gameobjects from a prefab that are moved along with received Pharus tracks. It is parented under MoxCameraHandler so that track objects maintain their position relative to the scene camera(s) if those are moved around.
    ├── Scene
	│   ├── Cube                # Simple cluster-synchronized object that moves up and down.
	│   ├── Capsule             # Cluster-synchronized object that demonstrates how to use user-defined synchronized data. In this case the capsule's color changes over time.
	│   ├── Drone               # Another cluster-synchronized moving object that holds an audio source component to test surround sound. The drone flies in a circle around the scene origin.
	│   └── SurroundSoundTest   # A simple object that holds an audio source component with an 8-channel audio file. The audio file can be triggered via keyboard.
	├── SphereSpawner           # An object to demonstrate cluster-synchronized creation/destruction of objects from a prefab. The used prefab is a simple sphere with collider, rigid body, and SyncBehaviour to demonstrate synchronized movement based on physics-simulation. Spheres are created/destroyed via keyboard input.
	└── LevelSwitcher           # An object to demonstrate how to load scenes (levels), additively or switching completely. It is controlled via keyboard-input.
```

The **SecondDemoScene** and **AdditiveDemoScene** are used by the *LevelSwitcher* object and only contain some moving objects similar to *Drone*.

### Synchronization

If you start from the **EmptySample** scene (or a copy), all necessary Manager and Utility classes for synchronization, input, and cluster rendering are already in the scene.

To create a new synchronized GameObject you must add a **Mox.SyncBehaviour** component.

To spawn a synchronized GameObject at runtime, create a prefab GameObject with a **Mox.SyncBehaviour** component (or derivative), and spawn it via **Mox.Sync.SceneSyncManager.InstantiatePrefab**.

To switch scene (or load a scene additively) use **Mox.Sync.SceneSyncManager.LoadScene**.

#### SyncBehaviour

**Mox.SyncBehaviour** derives from MonoBehaviour and adds an interface that allows automatic synchronization of the visual and audio relevant components of the GameObject (meshes, lights, cameras, audio components). This may be enough for simple objects, e.g. objects that just follow game physics.

To achieve synchronized GameObjects with complex behaviour you must create a new script and derive from **Mox.SyncBehaviour** instead of **MonoBehaviour**. You can implement your desired behaviour like you would in any other **MonoBehaviour** derived script. **Mox.SyncBehaviour** provides an interface to synchronize user-defined data over the Mox Cluster (e.g. to synchronized script-controlled color changes or what have you).

To utilize user-data synchronization create a serializable struct (or class).

- **GetUserData():** used by the **Mox.Sync.SceneSyncManager** to get user data object for serialization and synchronization
- **GetUserDataType():** used by the **Mox.Sync.SceneSyncManager** for user data deserialization
- **SetUserData(object userData):** called by **Mox.Sync.SceneSyncManager** when a user data updated is received
- **SyncInitDone():** called by **Mox.Sync.SceneSyncManager** when the sync object has been prepared for cluster synchronization. At this point it is safe to gather references to visual/audio components (mesh, light, camera, audio) if needed.

You may want to avoid local changes to your user data in secondary Game Instances by checking if the code is running on the primary instance (**Mox.Sync.SceneSyncManager.IsPrimary**).

**NOTE** that **Mox.SyncBehaviour** overrides the **MonoBehaviour** functions *OnValidate()* and *OnDestroy()*. It is **important to call** *base.OnValidate()*/*base.OnDestroy()* if you need to override either of those two functions **in your own class**.

**NOTE** that **Mox.SyncBehaviour** get's a unique ID, **SyncID** assigned by **Mox.Sync.SceneSyncManager** when it is created. Copying **Mox.SyncBehaviour** objects is handled automatically. When copying an entire *Scene* this cannot be done until the new *Scene* is opened for the first time. Duplicated **SyncIDs** can lead to undesired behaviour, even when switching from one scene to another!

#### SceneSyncManager

**Mox.Sync.SceneSyncManager** is the central manager class that handles cluster synchronization of **Mox.SyncBehaviour** objects. It has some static utility functions that will help perform some cluster-synchronized tasks beyound what individual GameObjects do.

- **InstantiatePrefab(GameObject prefab, ObjectInstatiatedCallback callback):** spawns a GameObject from a given prefab. The prefab does *not* need to have a **SyncBehaviour** component (**NOTE** that if the prefab does not have a **SyncBehaviour** you need to handle de-spawning yourself if necessary). A callback function can be provided to be notified when the new GameObject was actually spawned.
- **RemoveSyncObject(string id):** de-spawns a GameObject with **SyncBehaviour** component by a given **SyncID**. Therefore this function cannot handle GameObjects without **SyncBehaviour**.
- **LoadScene(string sceneName, bool loadAdditive): ** loads the scene with the given name (alternatively the scene ID can be used). Can either load additively or just switch to the new scene.
- **UnloadScene(string sceneName):** unload the scene with the given name (alternatively the scene ID can be used). 

### Input

Since the Unity application is going to run in the background behind an Unreal application, user input (keyboard, mouse, gamepad) will be forwarded from the Unreal application.

The Mox Framework provides an input interface similar to Unity's own via the **Mox.Input** class.

- **KeyDown(KEYCODE key)**
- **MousePosition()**
- **MouseButtonDown(MOUSECODE key)**
- **GamepadButtonDown(GAMEPADCODE key)**
- **GamepadAxisValue(GAMEPADAXISCDOE key)**

**Note** that while it works to use keyboard/mouse/gamepad input directly via Unity in the editor it will not work when you want to use it in the real cluster setup. The Unity application will not be in the foreground.

### Tracking

Tracking data (OptiTrack and/or Pharus, depending on where you deploy your project) is provided through the **Mox.Tracking** class.

#### Pharus

Pharus tracks can be accessed via the **Mox.Tracking** class.

**PharusTracks()** returns a list of all current tracks.

A track consists of

- Id (int)
- Position (Vector3)
- Rotation (Vector3)

#### OptiTrack

OptiTrack tracks can be accessed via the **Mox.Tracking** class.

**OptiTrackTracks()** returns a list of all current tracks.

A track consists of

- Id (int)
- Position (Vector3)
- Rotation (Vector3)

### Audio

To use regular Unity Audio no special handling is required. In a cluster setup, typically the computer running the primary instance will be plugged into the audio system.

The **Mox.Audio** class provides an interface for clusters setups with [Ableton](https://www.ableton.com/)/[L-Isa](https://www.l-acoustics.com/products/l-isa-studio/) support.

The Ableton/L-Isa interface provides functionality to start/stop tracks, set corresponding parameters (e.g. position, volume, constum...), control effects, etc.

## Simulation

The MozXR Framework provides a preview mode (simulation) of a given NDisplay cluster, as defined by an *.ndisplay config file ([NDisplay](https://dev.epicgames.com/documentation/en-us/unreal-engine/ndisplay-overview-for-unreal-engine) ).

NDisplay configuration should be provided by the operators of the space you are planning to deploy your project to (e.g. [Deep Space](https://ars.electronica.art/center/en/deepspace/) ).

During simulation, Unity sends render output to the Unreal Endpoint (*Download to be provided*) via [Spout](https://spout.zeal.co/). The Unreal Endpoint will display the Unity output according to the active simulation mode.

### Cluster Endpoint

The cluster Endpoint application, as specified in the Configuration settings, can be launched manually.

```
Tools
└── MozXR
    └── Control Panel
	    └── Simulator
            └── [Start Endpoint]
```

Otherwise it will launch automatically once editor enters play mode (as single or cluster-preview).

### Render Modes

You can run the simulation in a simple **single-camera** mode or a full NDisplay **cluster** simulation.

In **single-camera** mode the Unreal Endpoint will display the output of a single cluster camera, filling the entire viewport. By default it will be the camera belonging to the primary NDisplay node. Unity also only renders this one camera.

In **cluster** mode the entire NDisplay cluster is diplayed by the Unreal Endpoint. The Unity output will be rendered on screens in a 3d-scene, according to the screens in the given NDisplay configuration. This 3d-scene can be maneuvered in to get a preview of the screens/projections in physical space. Unity has to render all cluster cameras. It may be necessary to reduce per-camera resolution for performance.

### Render Controls

To run **single-camera** mode just hit the *Play* button in the Unity Editor, or the *Start Single* button in the MozXR control panel.

**cluster** mode is launched via the MozXR control panel.

```
Tools
└── MozXR
    └── Control Panel
	    └── Simulator
            ├── [Start Single]
            └── [Start Cluster]
```

The Unreal Endpoint will automatically switch to the mode Unity is running in and load the correct NDisplay config (see [Configuration](#configuration) ).

### Tracking Modes

Tracking simulation can be controlled via the MozXR control panel.

```
Tools
└── MozXR
    └── Control Panel
        └── Tracking
```

You can start Pharus in simulation mode via the opened control panel.

```
Tools
└── MozXR
    └── Control Panel
        └── Tracking
            └── Pharus
                ├── Unicast
                │   ├── [Start(Stop) All]
                │   ├── [Start(Stop) Floor]
                │   └── [Start(Stop) Wall]
                └── Multicast
                    ├── [Start(Stop) All]
                    ├── [Start(Stop) Floor]
                    └── [Start(Stop) Wall]
```

Pharus Application(s) will launch in simulation mode according to your chosen option. A pharus recording, according to the Mox [Configuration](#configuration) will play.

### Configuration

MozXR settings can be accessed via the MozXR control panel.

```
Tools
└── MozXR
    └── Control Panel
        └── Configuration
```

The following options are available.

```
Tools
└── MozXR
    └── Control Panel
        └── Configuration
            ├── Endpoint                              # Endpoint (Unreal) related Settings
            │   └── Endpoint Directory                # Directory of the Endpoint Binaries
            ├── Pharus                                # Pharus Simulation related Settings
            │   ├── Base Directory                    # Directory of the Pharus Binaries
            │   └── Recording                         # Name of the pharus recording to be played during simulation (found next to Pharus Binaries)
            ├── NDisplay
            │   └── NDisplay Config                   # Path of the NDisplay configuratoin (*.ndisplay file) used during simulation
            └── MozConfig							  
                └── MozConfig                         # Path of the config .ini file used by the Unreal Endpoint application
```

The settings are stored in the Assets/MoxEditor directory. The directory and file will be created automatically and populated with default settings if it does not exist.

The Mox config file uses json. Editing with a text editor is *not* recommended while the Unity Editor is running (to ensure that all settings used by Unity are in sync with the settings in the file).
